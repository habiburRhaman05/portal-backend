# Deployment Options

## Recommended: single Vercel project, backend serves the frontend

This is how the repo is set up right now. There is nothing separate to deploy for "the frontend" — `api/index.js` serves:
- `public/clients/index.html` (sign-in page) at `/clients`
- `public/clients/portal/index.html` (the portal, generated by `scripts/prepare-portal.js`) at `/clients/portal`
- All `/api/*` routes

One Vercel project, one deploy, one domain. This is the right choice here because:
- The portal isn't a static site — it needs a signed-in session and server-fetched prefill data before it can render anything useful. Splitting it out just adds a network hop and a second CORS surface for no benefit.
- Auth cookies are simplest same-origin. Cross-origin cookies (frontend on Netlify, API on Vercel) need `SameSite=None; Secure` and more careful CORS, which is extra risk for zero gain here.
- One deploy pipeline, one set of env vars, one place to check logs.

### How to deploy
1. Push `portal-backend/` to a GitHub repo (or connect it directly if it's already the repo root Vercel should watch)
2. In the Vercel dashboard: **New Project** → import the repo → root directory `portal-backend` if it's nested
3. Add every variable from `.env.example` under **Settings → Environment Variables** (Production, and Preview if you want preview deploys to work)
4. Deploy. Vercel auto-detects `api/index.js` as a serverless function via `vercel.json`'s rewrite rule.
5. Point your `clients.browndiamondcapital.com` CNAME at the Vercel deployment (Vercel gives you the target after you add the custom domain in project settings)

No build step is required — `public/clients/portal/index.html` is already committed (it's the output of `scripts/prepare-portal.js`, run locally). If you change the source portal HTML in `docs/handoff/`, re-run `npm run prepare-portal` locally and commit the updated output before deploying.

### Or deploy via CLI instead of git
```bash
npm i -g vercel
cd portal-backend
vercel login
vercel --prod
```
This uploads whatever's in the working directory (respecting `.vercelignore`) without needing GitHub at all.

## Alternative: split frontend and backend

Only worth doing if you specifically want the portal on a CDN-edge static host separate from the API (e.g. different teams own them, or you want Netlify specifically for the static site). Tradeoffs below.

### What would move
- `public/clients/index.html` and `public/clients/portal/index.html` → Netlify (or Vercel static, or any static host)
- Everything else (`api/`, all the `/api/*` routes) → stays wherever the backend runs (Vercel, Render, Fly.io, a VPS)

### What breaks and has to be fixed
1. **Cookies become cross-origin.** The auth cookie is `httpOnly; SameSite=lax`. Lax cookies aren't sent on cross-site fetch/XHR at all in some browsers for non-top-level navigation — you'd need `SameSite=None; Secure`, which requires HTTPS everywhere (fine) and makes CSRF protection weaker, so you'd want to add an actual CSRF token at that point.
2. **CORS gets stricter to configure correctly** — `Access-Control-Allow-Origin` would need to be the exact static-site origin, and every fetch call in the portal would need `credentials: 'include'` instead of `same-origin`.
3. **Two deploys to keep in sync** — a broken deploy of one half against the other half is now possible; there's no single "it works" state to check.
4. **The `/clients/portal` route currently does `requirePageAuth` server-side (redirects signed-out visitors before the HTML ever loads).** A static host can't do that — it would serve the HTML unconditionally, and you'd have to do the auth check client-side after the page loads (worse: it flashes the portal shell before redirecting, or you add a loading spinner to mask it).

### How to do it anyway, if you want to
**Static site on Netlify:**
```bash
# from a folder containing just the two HTML files
netlify deploy --prod --dir=public/clients
```
Set `PORTAL_ORIGIN` in the backend's env vars to the Netlify URL, and change the two `fetch()` calls in the wiring patch (`scripts/prepare-portal.js`) and the sign-in page to use an absolute backend URL + `credentials: 'include'` instead of relative paths + `same-origin`.

**Static site on Vercel (separate project from the API):**
Same idea — a second, static-only Vercel project pointed at `public/clients/`, with the same cross-origin cookie/CORS changes.

---

## Recommendation
Keep the single-project setup. It's already built, it's simpler to operate, and nothing about this app benefits from a CDN-static frontend — the portal is dynamic and gated behind auth on every load anyway.
